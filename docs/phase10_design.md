# Phase 10 design: bounded and conclusive labels for C1 to C5 on one virtual machine

Status: written and frozen BEFORE any measured run; its sha256 is logged in `logs/p10/p10_design_sha256.log` before the first measured block. Probe, smoke and calibration runs are excluded from every verdict by pre-declaration (their outputs live in `logs/p10/probe*/`, `logs/p10/smoke/` and `logs/p10/*/calib_*`). Any later change is a dated amendment in section 9, written before the affected runs, with the old numbers kept alongside. Rule IDs start with `P` to avoid clashes with V1 to V8, K1, R-C2 to R-C4, S1 to S3 and N1 to N4.

## 1. Purpose, scope and labels

Goal: end each of the claims C1 to C5 of `CLAIMS.md` with one of **SUPPORTED**, **NOT SUPPORTED** or **BOUNDED** (an effect that is present or absent only inside a declared margin) wherever the mechanism exists on this machine. **INCONCLUSIVE** stays possible only as the result of a declared rule that the data cannot decide; every rule below says when. One machine only (aarch64 virtual machine, 5 CPUs, kernel as recorded in `ENV.md`), so a result is about this machine and says nothing about other machines.

What is new relative to Phases 6 to 9: sharper instruments (kernel-side `BPF_PROG_TEST_RUN`, a drain microbenchmark, a copy microbenchmark) for the size slopes of C2 and C3; a topology in which the capture runs on the receiving end with receive-packet-steering (RPS) so that receive-side work leaves the sender's core (C4); a ladder of paced rates below the sender's ceiling (C4); a hardened instruction-count study (C1); and a verifier test of termination (C5).

Declared margins (my choices, flagged for the reviewer; they are the only places where a number decides a label): slope margin **delta = 10 ns/byte** (set by the reviewer's instruction; about one fifteenth of the 1993 BPF slope of 148 ns/byte and one twenty-second of the NIT slope of 216 ns/byte, `CLAIMS.md` C3, paper.txt L186-189 and L208); cost-ratio margin **10 percent**; mitigation margins 1.10 and 1.25 (section 5); drop-fraction margin 0.1 percent (section 5).

## 2. Statistics, common to all work packages

- **Intervals.** "90% interval" of a slope is the two-sided 90% Student-t interval of an ordinary least-squares fit (degrees of freedom = points - 2); "95%" analogously. Difference of two independent slopes: difference of the estimates, standard error = sqrt(se1^2 + se2^2), Welch-Satterthwaite degrees of freedom (as `diff_ci` of `scripts/summarize.py`). Ratios of means: delta-method interval (`ratio_ci` of `scripts/summarize.py`).
- **Slope classes (rule P1).** For a slope-like quantity q with interval [lo, hi]: **INSIDE** if lo >= -delta and hi <= +delta; **OUT+** if lo > +delta; **OUT-** if hi < -delta; **UNDECIDED** otherwise.
- **Ratio classes (rule P2).** For a cost ratio rho = cost(A)/cost(B) with 95% interval [lo, hi] and margin m = 0.10: **B-CHEAPER** if lo > 1+m; **A-CHEAPER** if hi < 1/(1+m); **EQUIVALENT** if lo >= 1/(1+m) and hi <= 1+m; **UNDECIDED** otherwise.
- **Order and sizes.** In every microbenchmark the (size, batch) cells are run in a random order drawn once from the seed `20261108` by the plan script of the block and written to the log with its sha256 before the block starts.
- **Validity (rule P3).** A run or batch is valid if it passes the rules of its work package and the canary rule of its block (section 8). A cell needs at least the minimum number of valid repetitions named in its work package; fewer makes that cell, and every verdict that needs it, INCONCLUSIVE with the root cause printed. No run is dropped for its value.
- **1993 comparison.** Whenever a slope is reported, the script also prints the upper end of its interval divided by 148 and by 216 ns/byte, labelled DESCRIPTIVE.

RPS on the receiving veth device is writable and steers the receive work: with mask 2 (core 1) all 2.76 million packets processed by softnet in a 3 s flood were processed on core 1; with mask 0 all 1.32 million were processed on the sender's core 4, and the offered load of the flood was 1.32 and 2.76 million packets in 3 s respectively (probe numbers, not results, no capture attached). The `pktgen` module is installed and loadable; `trafgen` and `mausezahn` are absent; a C pacer built on `sendmmsg` is possible. gcc 15.2.0, clang 20.1.8, libpcap 1.10.5, tcpdump 4.99.5, kernel 6.17.0-41-generic (it was -19 in Phases 6 to 8.4; the change is recorded, no earlier number is reused as a baseline). ## 4. WP1: C2 and C3, sharper size slopes (`src/p10_memcpy.c`, `src/p10_testrun.c`, `src/p10_drain.c`)

Frame sizes (bytes of the Ethernet frame, as in Phase 6): **64, 256, 512, 1024, 1500**. At least **10 valid batches per (path, size)**, run in the random order of section 2. Each tool prints one CSV row per batch.

- **(a) Copy floor (`p10_memcpy`)**: user-space `memcpy` of `size` bytes between two cache-resident buffers, 20 million repetitions per batch, ns per call. Context only: it gives the slope floor of a pure copy; it has no label.
- **(b) In-kernel filter cost (`p10_testrun`)**: `bpf_prog_test_run_opts` with `repeat = 3,000,000`, data = a UDP/IPv4 frame of `size` bytes addressed to port 4040 (the program sees `size - 14` bytes because the socket-filter test run strips the Ethernet header, D3.4); programs: `reject_all` and `accept_all` of `build/phase6_filters.o` and `phase3_filter` of `build/phase3_kern.o` (port 4040 filter). Output: the average ns per repetition (`duration`, an integer of nanoseconds averaged over the repetitions), `retval` checked equal to the expected value (0 for reject, non-zero for accept, per program) in every batch, otherwise the batch is invalid.
- **(c) Drain cost (`p10_drain`)**: for each batch, N = 20000 UDP frames of `size` bytes to 10.0.0.1:4040 are sent from inside namespace `p2ns` over the veth pair and queue on an AF_PACKET socket (protocol ETH_P_IP, bound to `p1veth0`, receive buffer forced to 256 MB with `SO_RCVBUFFORCE`) that nothing reads; a UDP socket bound to 10.0.0.1:4040 (never read, large buffer) avoids ICMP replies. After the sender has finished and the queue has settled, `PACKET_STATISTICS` is read once: the batch is valid only if `tp_drops == 0` and `tp_packets == N`. Then the queue is drained with `recvfrom(MSG_DONTWAIT)` until `EAGAIN` and the elapsed time (`CLOCK_MONOTONIC_RAW`, process pinned to core 2) divided by the number of packets received is the drain cost in ns per packet. Paths: **U** (no BPF filter; after each receive a user-space filter checks ethertype, IP protocol and UDP destination port 4040, like `baseline_sniffer`), **E** (accept-all eBPF filter attached with `SO_ATTACH_BPF`, no user-space filter) and **B** (the port-4040 eBPF filter, all frames match). The reject-all path has an empty queue by construction and is represented by (b).
- **Slopes.** For every (quantity, path) an OLS fit of cost against size over all valid batches: kernel filter cost per program (b), drain cost per path (c), copy cost (a). Intercepts are reported with their intervals; they carry no label (1993: 5.7 us BPF and 89.2 us NIT).
- **Rule P4 (C2, "reject all": the in-kernel cost is flat in size and the user-space copy-then-filter cost grows).** Let s_K be the slope of `reject_all` in (b) and s_U the slope of path U in (c) (receive plus user-space filter, the cost the user-space design pays per packet it rejects); d = s_U - s_K. Labels: **SUPPORTED** if class(s_K) = INSIDE and class(d) = OUT+ (flat in the kernel, growing in user space by more than delta); **BOUNDED** if class(s_K) = INSIDE and class(d) = INSIDE (neither grows by more than delta, so the 1993 growth is excluded above the margin); **NOT SUPPORTED** if class(s_K) is OUT+ or OUT- (the kernel filter cost is not flat); otherwise **INCONCLUSIVE**.
- **Rule P5 (C3, "accept all": copy slope and fixed cost, user-space path against the in-kernel path).** Let e = s_U - s_E (both from (c)). Labels: **SUPPORTED** if class(e) = OUT+ (the user-space path grows faster by more than delta, the direction of Fig. 2); **BOUNDED** if class(e) = INSIDE (the difference of the slopes is bounded by delta); **NOT SUPPORTED** if class(e) = OUT- (the in-kernel path grows faster by more than delta); otherwise **INCONCLUSIVE**. The class of each of s_U, s_E and s_B and the ratios to 148 and 216 ns/byte are reported next to the label.
- **Minimum**: 8 valid batches per (path, size); fewer makes the affected quantity INCONCLUSIVE.

## 5. WP2: C4 on one host (`scripts/p10_bench.sh`, a copy of `scripts/p8_2_bench.sh`)

Harness: `scripts/p10_bench.sh` is a copy of `scripts/p8_2_bench.sh` (itself a copy of the frozen `scripts/bench.sh`) with only these changes, listed in `logs/p10/p10_bench_vs_p8_2_bench.diff`: topology T0 or T1; both iperf3 clients pinned to core 4; RPS control; the traffic class `ladder`; output under `logs/p10/`. Everything else (classifier tap on `p1veth0`, pinned core 0; iperf3 servers in `p2ns` on core 3; capture process on core 2; run log format; `scripts/summarize.py` `parse_run` for V1, V2, V5'a to V5'e, V6, V7) is unchanged. Pinning for all WP2 runs: **system, bench and classifier core 0 (canary core), RPS core 1, capture core 2, iperf3 servers core 3, both iperf3 clients core 4.** Frame size 256 bytes (UDP payload 214), 10 s per run.

### 5.1 WP2(a): mitigation test, flood, topologies T0 and T1

- **T0** (as in Phase 8.2): capture on `p1veth0` in the root namespace; `rps_cpus` of `p1veth1` is 0. **T1** (mitigated): capture on `p1veth1` inside `p2ns` (`nsenter --net=/run/netns/p2ns`, core 2) and `rps_cpus` of `p1veth1` rx-0 set to core 1 (mask 2) for the run and reset to 0 afterwards.
- **Configs** N (no capture process, no capture filter), A (`baseline_sniffer`), B (`loader -d`, port-4040 filter), C (`loader`, no drain) in both topologies: 8 cells, **6 runs per cell, at least 5 valid**, all 48 rows in one randomized order (seed of section 2). Traffic: two unlimited iperf3 UDP streams (4040 match, 5050 noise), as `flood` in Phase 6.
- **Metric.** offered(X, T) = per-run client packets per second summed over both streams (as Phase 8.2), mean over valid runs. R(X, T) = offered(N, T) / offered(X, T) for X in {A, B, C}; Q(X) = R(X, T1) / R(X, T0). Intervals: delta method on the logarithm, var(log R) = cv_N^2/n_N + cv_X^2/n_X, var(log Q) = var(log R(X, T1)) + var(log R(X, T0)), 95% interval exp(log estimate +- 1.96 se).
- **Prediction (declared now).** With the receive-side capture work moved off the sender's core, the offered-load gap of the capture configs against N shrinks in T1: for X in {A, B}, **Q(X) < 1** and **R(X, T1) <= 1.10**. Reason: in T0 the capture taps run inside the sender's transmit call (Phase 8.2: R(A) 1.66, R(B) 1.46, run set 2, a different kernel and different pinning, not a baseline here); in T1 the tap of the capture config sits on the receive path and runs on the RPS core, so the sender core pays only the classifier tap that every config has. The probe of section 3 says the receive-side processing alone doubled the sender's rate.
- **Rule P6 (mitigation verdict).** Per X in {A, B}: **REMOVED** if hi(Q) < 1 and hi(R(X, T1)) <= 1.10; **REDUCED** if hi(Q) < 1, hi(R(X, T1)) > 1.10 and hi(R(X, T1)) <= 1.25; **NOT REDUCED** if lo(Q) > 0.90 (the gap shrank by less than 10 percent at most); otherwise UNDECIDED. Label of the sub-claim "the sender-side confound can be removed on this host": **SUPPORTED** if both are REMOVED; **BOUNDED** if both are REMOVED or REDUCED and not both REMOVED (residual gap bounded by 25 percent); **NOT SUPPORTED** if either is NOT REDUCED; otherwise **INCONCLUSIVE**. C is reported, never gating.
- **V8 for flood runs (rule P7).** The canary set is core {0}. Before the block, 3 calibration windows (excluded) of config N in T1 and 3 of config N in T0 are run; `canary_max_flood` = the largest canary rate on core 0 among these 6 windows, limit = 1.2 x canary_max_flood; a run above the limit is re-run at most twice (attempts kept), the last attempt is analysed, a cell still above is excluded. This replaces the uncalibrated 0.035 floor of Phase 8.3 (D8.22); the calibration windows and the limit are written to `logs/p10/wp2a/calib_v8.json` before the first measured run.

### 5.2 WP2(b): paced ladder, receiver drop fraction and capture CPU per packet

- **Topology T1 only**, configs A, B, C, traffic class `ladder`: two iperf3 UDP streams (4040 match, 5050 noise), each paced at half of the total target, **total targets 100000, 200000, 300000, 450000 and 600000 pps** (all below the lowest sender ceiling of Phase 8.2, A at about 1.23 million packets per second), **6 runs per cell, at least 5 valid**; 3 x 5 x 6 = 90 rows in one randomized order.
- **Rate held (rule P8).** A run is valid only if the achieved total offered rate is within 5 percent of the target. A rate at which fewer than 5 runs per config are valid is reported UNREACHABLE and is dropped; at least 3 reachable rates are needed for a label.
- **V8 (rule P7)** with its own 3 calibration windows (excluded) of config A at 300000 pps.
- **Metrics per run.** (i) Socket drop fraction d = `kernel_drops` / `kernel_packets` of the capture socket (A and B; for C the queue is never read and drops are by construction: C is reported for CPU only). (ii) Capture-side CPU per flow-matched packet: the busy CPU time of the two receiver-side cores (RPS core 1 plus capture core 2, from the per-CPU counters of the run log) minus the idle busy time of the same cores (mean over the idle windows of the block's pre-flight, times the run window), divided by the flow-scoped matched packet count (`matched_flow` of `parse_run`).
- **Rule P9 (C4 label).** At each reachable rate r: rho_r = cpu(A)/cpu(B), class by rule P2. Label **SUPPORTED** if at least half of the reachable rates are B-CHEAPER and none is A-CHEAPER; **NOT SUPPORTED** if at least half are A-CHEAPER; **BOUNDED** if at least half are EQUIVALENT and none is B-CHEAPER or A-CHEAPER; otherwise **INCONCLUSIVE**. The drop fractions are reported as separate classes (not gating): per rate, **NO-LOSS-BOUND** if the upper end of the Clopper-Pearson 95% interval of d (pooled packets of the cell) is at most 0.001 for both A and B; **B-BETTER** if lo(d_A - d_B) > 0.001; **A-BETTER** if lo(d_B - d_A) > 0.001; otherwise UNDECIDED.
- The C4 label of Phase 10 is the label of rule P9; the mitigation label of rule P6 is reported beside it and states whether the sender confound of Phase 8.2 is present in the ladder topology.

## 6. WP3: C1 hardening (`scripts/p10_c1_grid.sh`, `scripts/p10_c1_indep_check.sh`, `scripts/p10_traffic_anon.py`)

All parts use the Phase 6c pipeline (`scripts/c1_build.sh`, `c1_run.py`, `c1_summarize.py`; interpreters, decision-equivalence check against libpcap, callgrind M2 with the evaluator-only attribution of amendment A3); nothing of its rules changes, only inputs and builds do. Primary pairing: mix M0, BPF-opt against CSPF `sc-fused`, M2 = host instructions per packet inside the evaluator, ratio R = CSPF/BPF with a 95% t-interval over the ten 1000-frame chunks.

- **(a) Build grid.** Interpreters built with gcc 15.2.0 and clang 20.1.8 at -O0, -O2, -O3 (6 builds) and BPF programs from libpcap with the optimizer on (BPF-opt) and off (BPF-raw): for every build and each filter F1 to F4, R(BPF-opt) and R(BPF-raw). Decision equivalence against libpcap must give 0 mismatches for every build or the build is excluded and the verdict cannot be SUPPORTED.
- **(b) Independent CSPF set.** A fresh subagent that has never seen `src/c1_progs/` writes the four CSPF programs from the paper excerpts (paper.txt L295-345, L395-407, L703-737) and the opcode list and file format of section 3.2 of `docs/phase6c_design.md`; the programs are stored in `src/p10_indep/`, hashed, checked for decision equivalence against libpcap on all three Phase 6c mixes, and run through the same primary pairing. Ratios are reported next to ours.
- **(c) Real traffic mix.** 20000 frames (or all that arrive in 10 minutes) captured by `tcpdump` on `enp0s8`, all addresses rewritten by `scripts/p10_traffic_anon.py` to the 10.0.0.0/8 range (a deterministic keyed mapping), H and G = the two most frequent anonymized hosts (ties broken by lower address); the pipeline is run on this trace as a fourth mix. The raw capture is never committed; the repository keeps the sha256 of the anonymized trace and the summary only. The capture is prepared before the measured run (it needs real traffic) and its hash is logged before the block.
- **Ordering report.** For every cell and for the independent set: the sign and interval of R(F2) - R(F3), and a table of which factors (compiler, optimization level, libpcap optimizer, CSPF set, mix) flip the ordering F2/F3.
- **Rule P10 (C1 sub-claims).** C1a (direction): in a cell, **HOLDS** if the lower end of the interval of R is above 1 for all four filters, **REVERSED** if the upper end is below 1 for at least one filter, otherwise UNDECIDED. C1b (ordering): **HOLDS** if the point estimates satisfy R(F1) < R(F2) < R(F3) < R(F4). Cells considered: the 6 builds with BPF-opt and our CSPF set (the BPF-raw cells, the independent set and the real mix are reported with the same classes and with the flag AGREES or DISAGREES with the grid majority, and do not change the label).
- **Rule P11 (C1 label).** **SUPPORTED** if C1a and C1b HOLD in all 6 cells; **NOT SUPPORTED** if C1a does not HOLD in at least 4 of the 6 cells; **BOUNDED** otherwise, the bound being the range of R(F) over the cells for each filter (minimum of the lower ends to maximum of the upper ends) and the list of cells in which C1a or C1b fail (for this claim the "declared margin" is the factor grid: the direction and the order are bounded to the combinations that the table lists).

## 7. WP4: C5, termination by the verifier (`src/p10_loop_unbounded.c`, `src/p10_loop_bounded.c`, `scripts/p10_c5.sh`)

Two socket-filter programs are built with clang (`-target bpf -O2`), the first with an unbounded loop (no exit condition the verifier can bound), the second with a loop of a constant, small bound; both are loaded with `bpftool -d prog load` (verifier log level of bpftool) and the verifier's stderr and exit status are stored verbatim in `logs/p10/wp4/`. Header symbols and the kernel's loop support are checked and recorded in `CODE_NOTES.md` and `ENV.md` first. **Rule P12 (C5, termination part):** **SUPPORTED** if the unbounded program is rejected and the bounded program is accepted; **BOUNDED** if both are rejected (termination is enforced conservatively, loops are not accepted at all); **NOT SUPPORTED** if the unbounded program is accepted. The C5 label is the label of rule P12; the CPU-benefit part of C5 of Phase 8.7 is the label of C2 and C3 of rules P4 and P5 and is stated beside it. Phase 5 evidence (acceptance and rejection of the Phase 5 programs) is not re-run.

## 8. Hands-off protocol, blocks, outputs and checks

- **Launch.** One command, `sudo bash scripts/p10_run_all.sh`, from a fresh Terminal tab; I make no tool call while it runs. It refuses to start if any of `logs/p10/wp1`, `wp2a`, `wp2b`, `wp3`, `wp4`, `logs/p10/run_all` or `results/p10_*` exists and is non-empty.
- **Every block** (B1 WP1, B2 WP2(a), B3 WP2(b), B4 WP3, B5 WP4) starts with a 60 s settle, the memory gate (swap in use <= 2000 MB and MemAvailable >= 1500 MB, from `free -m`, recorded before and after the block), and a pre-flight idle set of 3 windows of 10 s with the harness attached; the canary rate on the cores the block does not use must not exceed the Phase 6 idle limit of 1.2 x 0.0689 = 0.0826 CPU-s/s (two cores; for three cores the limit is scaled by 3/2), or the whole run aborts loudly before the block. The block's canary limit for batches of WP1 and WP3 is 1.2 x the largest canary rate of its own pre-flight windows; a batch above it is re-run at most twice and then excluded (rule P3). WP2 uses rule P7.
- **No silent failure.** Scripts stop at the first failing command (no output is sent to `/dev/null`; every tool writes its own log), delete their outputs first and check that they were created. `scripts/p10_summarize.py` computes every number and every label from the logs; verdict strings contain no typed numbers and no narrative (rule P13); `scripts/p10_verify.sh` checks the design hash chain, the label rules against the files, the absence of typed numbers in verdict strings, the validity counts and that no output predates its input.
- **Plans and seeds.** Seed 20261108. Plans (`results/p10_plan_*.tsv`) are written by `scripts/p10_plan.py` before the launch; their sha256 values are logged with the design hash.
- **WP5 (confirmatory V8 run)** is not part of this design; it would be added by a dated amendment, with its blocked design, before any of its runs, if the reviewer asks for it.
- **Estimated hands-off time:** written into the launch announcement after the tools exist and have been smoke-tested (smoke runs are excluded).
