# Phase 8.4 design: does the V8 canary rule do what it is supposed to do?

Status: written and frozen BEFORE any calibration probe, noise run or analysis; its sha256 is logged in `logs/p8/p8_4/p8_4_design_sha256.log` before the first run. Any later change is a dated amendment at the end of this file, with the evidence, written before the affected runs; old numbers stay alongside. Rule IDs start with `N` (noise validation) to avoid collisions with V1 to V8, S1 to S3 and the earlier IDs.

## 1. The rule under test and the question

V8 (`docs/phase6_addenda.md` section 2): the cores that the experiment does not use are controls. A measured window whose canary rate (busy CPU-seconds on the canary cores / window seconds, from `/proc/stat`) exceeds 1.2 x canary_max is contaminated and is repeated. canary_max comes from the three quiet calibration idle windows (`results/baseline_calibration.json`): 0.0689 CPU-s/s for the set {0,1} and 0.0369 for {0}, so the limits are **0.0826 for {0,1}** (paced curve runs) and **0.0443 for {0}** (flood runs, where core 1 runs the noise-stream iperf3 client). The premise of V8 is that CPU noise on cores the experiment does not use is a visible marker of noise that also corrupts the headline metrics. Phase 8.4 tests that premise directly instead of assuming it.

## 2. Experiments

**E1, paced curve (headline metric = net CPU per packet).** Config B (`build/loader -d p1veth0 build/phase3_kern.o`, drained, port-4040 filter), traffic `m` (UDP to the matching port 4040), 512-byte frames (the size of the Phase 6 warm-up and envelope runs), 32000 packets per second (`p_curve` of `results/calibration.json`), 10 s, pinning as in Phase 6 (client core 4, capture core 2, servers core 3, classifier tap and system core 0, core 1 free). **Metric M_sys** = net CPU ns per flow-scoped matched packet: (system-wide busy CPU-seconds - 0.1307 x window) x 1e9 / flow-scoped matched, with the idle baseline 0.1307 CPU-s/s of `results/baseline_calibration.json` (M1 and M2 of the addenda; D6.13). Secondary metric **M_exp** = busy CPU of the experiment cores {2,3,4} in ns per flow-scoped matched packet (gross, no idle subtraction); it shows whether noise on the canary cores reaches the experiment cores.

**E2, flood (offered pps).** Config N of Phase 8.2 (`scripts/p8_2_bench.sh` copy: classifier tap, two unlimited iperf3 streams, no capture process), 256-byte frames, 10 s. **Metric** = offered packets per second summed over both streams (as in `docs/phase8_2_design.md`).

**E3, noise V8 cannot see (separate short test, section 5c)** on E1.

## 3. Noise

Noise is made with `stress-ng` workers, each started under `taskset -c <core>` (the cache stressor with `--cache-no-affinity`, otherwise it moves itself), and **duty-cycled** by `scripts/p8_4_noise.py` (SIGSTOP/SIGCONT of the worker with a 100 ms period) so that its intensity is controlled. Two types: **cpu** (`stress-ng --cpu 1`, pure CPU load) and **cache** (`stress-ng --cache 1 --cache-no-affinity`, cache thrashing: memory and cache pressure). One worker per noised core. The noised cores are the canary cores of the experiment: **{0,1} for E1 and {0} for E2.**

**Levels.** Level 0 = the workers are started and held stopped (duty 0), so that the harness is identical to the noisy levels. The nominal duty per worker is chosen from a grid by a calibration probe (section 7, excluded from analysis) so that the *measured added canary rate* (CPU-s/s on the noised cores, summed) is closest, in ratio, to these targets:

| experiment | targets of the added canary rate (CPU-s/s) | V8 limit it should straddle |
|---|---|---|
| E1 (cores {0,1}) | 0.01, 0.025, 0.05, 0.10, 0.20 (5 levels + level 0) | 0.0826 (the idle canary rate in the quiet state is about 0.03 to 0.07 on {0,1}) |
| E2 (core {0}) | 0.01, 0.025, 0.05, 0.10 (4 levels + level 0) | 0.0443 (the idle canary rate on {0} is about 0.01 to 0.04) |

Grid of nominal duty per worker: 1, 2, 3, 4, 5, 7.5, 10, 15, 20, 30, 40 percent. The levels actually used and their measured added rates are recorded in an amendment written before the first measured run (selection rule above); if the calibration shows that a target cannot be reached within a factor of 2, the amendment says which levels were dropped, and fewer than four non-zero levels per type cancels the claim to test straddling for that experiment.

## 4. Windows and order

- **E1:** 30 windows per (type, level) = 2 types x 6 levels x 30 = 360 windows. **E2:** 2 types x 5 levels x 30 = 300 windows. **E3:** 60 windows (15 per condition, section 5c).
- Split into 7 launches, each with all cells present and randomised within the launch (seeded, `scripts/p8_4_plan.py`, plan files `results/p8_4_plan_<batch>.tsv` with logged sha256): **C1, C2, C3** (E1, 120 windows = 10 per cell, about 50 minutes each), **F1, F2, F3** (E2, 100 windows = 10 per cell, about 35 minutes each), **X1** (E3, 60 windows, about 25 minutes). Total about 4.5 hours of measurement. The launch is a block in the analysis (drift check), not a fixed effect in the tests.
- **No window is repeated or removed because V8 flagged it**: V8 is evaluated as a classifier on every window, which is the point of the experiment.
- Analysis windows must satisfy the harness-integrity rules V1, V2, V5'a to V5'e and V6 (as implemented in `scripts/summarize.py parse_run`, imported). V3, V4, V7 are **not** applied (noise may legitimately cause socket drops or a changed offered rate; excluding such windows would hide effects); their counts per cell are reported. A cell with fewer than 25 analysis windows is reported INCONCLUSIVE.
- **Hands-off protocol** as in Phase 8.2: each launch starts with the output-folder check (refuses to start if its folders are non-empty), the design and plan hash checks, the memory gate (swap in use at most 2000 MB, MemAvailable at least 1500 MB), a 60 s settle and a pre-flight of 3 idle windows of 10 s that must satisfy V8 (canary {0,1} at most 0.0826); the assistant makes no tool call and prints nothing while a launch runs.

## 5. Rules (declared now)

**Flag.** A window is *flagged* when V8 would contaminate it: canary rate on the experiment's canary set > 1.2 x canary_max of that set (0.0826 for E1, 0.0443 for E2), using the measured canary rate of the window, exactly as in `summarize.py`.

**N1, detection (question a).** For every (experiment, type, level) cell: flagged fraction p with a Wilson 95% interval. Cell class: **FLAGGED** if p >= 0.9, **UNFLAGGED** if p <= 0.1, **TRANSITION** otherwise. The **false-positive rate** is p at level 0; V8 is called acceptable at level 0 if the upper Wilson bound is <= 0.10 in each (experiment, type). Also reported: the mean measured canary rate per cell and the level at which p crosses 0.5 (linear interpolation on the measured added rate).

**N2, validity (question b, the important one).** For each cell and its level-0 reference (same experiment and type): ratio R = mean(level) / mean(level 0) of the experiment's metric (M_sys for E1, offered pps for E2) with a 95% interval (Welch-Satterthwaite degrees of freedom, exact Student t quantile, delta method for the ratio). With the tolerance **delta = 5%** (a shift of that size is within the half-width of the C4 factor interval of Phase 6, 8%, and could move a verdict boundary):
- **MATERIAL** if the interval excludes 1 and |R - 1| > delta;
- **EQUIVALENT** if the whole interval lies inside (1 - delta, 1 + delta);
- **INDETERMINATE** otherwise.

**V8's premise is SUPPORTED for a family (experiment, type) iff every FLAGGED level is MATERIAL and every UNFLAGGED non-zero level is EQUIVALENT**; TRANSITION and INDETERMINATE levels are listed and do not decide. **V8's premise is SUPPORTED overall iff it is supported in all four families.** It is NOT SUPPORTED if any FLAGGED level is EQUIVALENT (needless exclusion, reported with the level) or any UNFLAGGED non-zero level is MATERIAL (a blind spot, reported); otherwise PARTIAL (only indeterminate or transition levels prevent a decision). Reported but not gating: M_exp for E1 (whether the experiment cores are affected beyond the added CPU), the "mechanical" shift expected from the added canary CPU alone ((canary rate of the level - canary rate of level 0) x window x 1e9 / matched packets, relative to the level-0 mean), counts of V3, V4, V7 failures and the socket-drop fraction per cell, and the level-0 mean per launch (drift).

**N3, noise V8 cannot see (question 3, at least 15 windows each, on E1 with the canary cores quiet).** Conditions: **S0** control (workers held stopped on core 2); **S1** cpu noise on measurement core 2 (the capture process core); **S2** cpu noise on measurement core 3 (the iperf3 server core), both at the calibrated duty whose measured added rate is closest to 0.10 CPU-s/s; **S3** global memory pressure: one `stress-ng --vm 1` worker pinned to core 3 with `--vm-keep --vm-hang 0`-style holding of `bytes = MemAvailable at start - 1000 MB` (capped at 2048 MB; the window is not started and the script aborts loudly if that is below 200 MB or MemAvailable would fall below 800 MB). 15 windows each (60 in launch X1). For each: flagged fraction, and R, class (MATERIAL, EQUIVALENT, INDETERMINATE) of M_sys against S0. **Blind** = unflagged (p <= 0.1) and MATERIAL.

**N4, ablation by script from existing data (`scripts/p8_4_ablation.py`).** Recompute with V8 switched off (the V8 reason removed from validity; `CANARY_FACTOR` set to infinity in the imported `summarize.py`; idle baseline = calibration, as published, D6.13) the verdicts of:
- **Phase 6 C2, C3, C4** in three variants: (P) V8 on, final runs only, which must reproduce the published verdicts (MIXED, INCONCLUSIVE, NOT SUPPORTED); if it does not, the ablation is not accepted; (A1) V8 off, final runs only; (A2) V8 off, final runs plus every earlier attempt in `logs/attempts/` as additional runs of its cell (attempts are separate runs under the same conditions; they are treated as independent, which is a caveat).
- **Phase 8.2 run set 2** (S-H1, S-H2, verdict) from `logs/p8/p8_2/run2/`: V8 on (must reproduce SENDER-LIMITED SUPPORTED), V8 off final only, V8 off with the attempts.
- **Phase 8.2 run set 1** from the surviving derived data only (its raw logs were deleted, D8.14): per-run offered pps of all final unprofiled runs from `logs/p8/p8_2/p8_2_diag_exploratory_offered.log` and per-run profile shares from `results/p8_2_summary.md`; stated as such.
Report published against recomputed labels and key statistics side by side; whether any label changes, and which runs the V8 switch adds.

## 6. Statistics

Means, standard deviations, Welch 95% intervals, ratio intervals by the delta method, and Wilson intervals computed by `scripts/p8_4_summary.py` from the logs only (exact t quantile from the incomplete beta function, checked against the table of `summarize.py` by a self-test). Nothing is typed in by hand.

## 7. Calibration probe (excluded from analysis)

`scripts/p8_4_calibrate.sh` (launched by the user, about 10 minutes, no traffic): for each noise type, each grid duty and each noised core set used (cores {0,1}, core {0}, core 2, core 3) three 10 s windows of the noise alone, with the measured per-CPU busy rate before and after; it also checks that the workers stay on their core (affinity and per-CPU distribution), that `stress-ng` workers survive SIGSTOP/SIGCONT, and one 10 s global-memory window with the S3 holding rule (MemAvailable before, during, after). Its numbers select the levels (section 3) by the stated rule and are not data for N1 to N3.

## 8. Limits to state in any report

Single host, a virtual machine, a veth pair, one boot, one config per experiment; the added noise is synthetic (stress-ng duty cycles pinned to single cores) and may differ from the real ambient noise of Phase 6; **M_sys is system-wide**, so CPU noise on any core adds to it mechanically, which is why M_exp is reported as well; the tolerance delta = 5% is a judgement; launches are blocks and the whole series spans hours, so slow drift is possible (reported per launch); 30 windows per cell resolve shifts of about the metric's coefficient of variation divided by sqrt(30) and no smaller ones.

## 9. Files

`scripts/p8_4_noise.py` (controller), `scripts/p8_4_bench.sh` (copy of `scripts/p8_2_bench.sh` with the noise hook), `scripts/p8_4_calibrate.sh`, `scripts/p8_4_plan.py`, `scripts/p8_4_run.sh`, `scripts/p8_4_summary.py`, `scripts/p8_4_ablation.py`, `scripts/p8_4_verify.sh`; outputs `logs/p8/p8_4/`, `results/p8_4_*`.

## 10. Amendments

- **A1 (2026-10-26, before the calibration probe and before any measured run; evidence: `logs/p8/p8_4/p8_4_controller_functional_test.log`, a few seconds per noise type to check that the controller starts, pins and stops its workers; not data).** (1) The **cache** noise is `stress-ng --cache 1 --cache-enable-all --cache-no-affinity` (the functional test printed "cache flags used: none; use --cache-enable-all to enable all cache flags for heavier cache stressing", so without the flag the stressor is light); the other parts of section 3 are unchanged. (2) The memory-holding condition S3 is `stress-ng --vm 1 --vm-bytes <N>M --vm-hang 3600` pinned to core 3, without `--vm-keep`, so that after the allocation it holds the memory without using CPU; the wording in section 5 N3 ("`--vm-keep --vm-hang 0`-style holding") is replaced by this. (3) The calibration probe has 78 windows (3 baseline, 2 types x (11 duties x 2 windows on {0,1} + 11 on {0}), 4 duties on each of cores 2 and 3, 1 memory window) and takes about 17 minutes, not 10. No rule, threshold, tolerance or level target changes.
- **A2 (2026-10-26, after calibration probe 1 and before calibration probe 2 and any measured run; evidence: `logs/p8/p8_4/calib/calib.jsonl`, `logs/p8/p8_4/p8_4_calibrate_console.log`, `results/p8_4_levels_calib1.md`).** Calibration probe 1 (78 windows; excluded data) subtracted a baseline taken from three duty-0 windows to obtain the added canary rate. The baseline was not stable: the three windows read 0.092, 0.027 and 0.090 CPU-s/s on core 0 (0.087, 0.027, 0.073 on core 1), and two replicate windows of the same setting (cpu noise, duty 10 on cores 0 and 1) read 0.119 and 0.218 on core 0, so the ambient noise of the machine varied by about 0.1 CPU-s/s per core between windows and the baseline-subtracted rates were unreliable (negative at low duty, non-monotone: for example -0.069 at duty 3 and +0.099 at duty 1 on {0,1}). The duty cycle itself was accurate where it is visible without subtraction (cpu noise on core 2: busy 0.057, 0.103, 0.201, 0.396 CPU-s/s at duty 5, 10, 20, 40). **Changes:** (1) the *injected rate* of a window is now the CPU time that the stress-ng workers themselves consumed (utime plus stime from `/proc/<pid>/stat`, read at the start and end of the window), divided by the window length; it does not depend on the ambient noise and replaces "measured added canary rate" in section 3 for the choice of levels; the controller also reports `worker_cpu_seconds` in `NOISE_STOP`, so every measured window records its injected rate, next to the measured canary rate; (2) calibration probe 2 (`scripts/p8_4_calibrate.py`, 51 windows, about 11 minutes: 3 baseline windows for information, 1 window per cell for each type, core set and grid duty, and duties 5 and 10 on cores 2 and 3) replaces probe 1 for the levels; probe 1 stays in the logs with its numbers (`results/p8_4_levels_calib1.md`), and its memory window (S3) is reused; (3) the selection rule (closest in ratio to the targets of section 3) is unchanged but applied to the injected rate. **Consequence stated in advance:** the ambient canary noise of this machine (up to about 0.1 CPU-s/s per core in probe 1) is of the order of the V8 limit, so the false-positive rate at level 0 may be high in the measured runs; that is a result of N1, not a reason to change the rule. No rule, threshold, tolerance or target changes.
- **A3 (2026-10-26, after calibration probe 2 and before the first measured run; evidence: `logs/p8/p8_4/calib2/calib.jsonl`, `logs/p8/p8_4/p8_4_calibrate2_console.log`, `results/p8_4_levels.md`, `results/p8_4_levels.json`; levels chosen by `scripts/p8_4_levels.py`).** Probe 2 shows that the injected rate (workers' own CPU time) is accurate and almost linear in the duty: about 0.01 CPU-s/s per percent of duty per worker for both noise types (for example cpu on {0,1}: 0.020 at duty 1, 0.101 at duty 5, 0.198 at duty 10). With the grid minimum of 1% per worker, two noised cores cannot inject less than 0.020, so the E1 targets 0.010 and 0.025 collapsed onto duty 1; the selection rule now requires **distinct, increasing duties** (greedy over the increasing targets, the duty with the smallest ratio error above the previous one), which gives for E1 the duties 1, 2, 3, 5, 10 (injected rate, cpu: 0.0200, 0.0400, 0.0630, 0.1010, 0.1979; cache: 0.0200, 0.0420, 0.0590, 0.1000, 0.1980; the first two are 2.0 and 1.6 (cpu) or 1.7 (cache) times their targets, still within the factor 2 allowed in section 3) and for E2 the duties 1, 3, 5, 10 (cpu: 0.0100, 0.0300, 0.0510, 0.1000; cache: 0.0110, 0.0300, 0.0500, 0.0980). **E3:** S1 and S2 use duty 10 on core 2 and core 3 (injected 0.0990 and 0.1000); S3 holds MemAvailable minus 1000 MB capped at 2048 MB (probe 1: MemAvailable 3096 to 1059 MB). **Ambient state:** the three baseline windows of probe 2 read 0.0567 (core 0) and 0.0517 (core 1) CPU-s/s, i.e. a canary rate of 0.108 for {0,1}, above the V8 limit 0.0826 before any injected noise, and about 0.05 on every other core; if the machine stays in that state, level 0 will be flagged often and the V8 false-positive rate (rule N1) will be high; the measured canary rate of every window is recorded, so the analysis shows where the flag threshold is crossed. No rule, threshold or tolerance changes.
- **A4 (2026-10-27, written AFTER the pooled analysis of all seven launches had been computed and seen; evidence: `results/p8_4_summary.md`, `logs/p8/p8_4/p8_4_verify.log`). This is a post-hoc re-analysis of the same data; the pooled analysis of sections 5 and 6 stays the pre-declared primary result and its numbers stay in `results/p8_4_summary.md`; the A4 results are labelled as post hoc, written to `results/p8_4_blocked.md` and carry less weight.** Evidence that motivates it: (1) all 36 families-launches show that the level-0 reference moves a lot between launches: flood offered pps at level 0 is 1.07 M (F1), 2.03 M (F2), 2.09 M (F3) for cpu noise; the curve metric at level 0 is 6865, -223, 5 ns (cpu noise, C1 to C3) and 4375, -330, -1021 ns (cache noise); (2) every non-zero level came out INDETERMINATE under the pooled Welch test because this between-launch variation enters the within-cell variance, although every launch contains every level in random order. **Changes (analysis only, no new run, no rule of sections 5 and 6 is removed):** (a) **Blocked comparison.** For each family (experiment, type) and level L, the shift is formed inside each launch b (a block of 10 windows per cell): d_b = mean_b(L) - mean_b(level 0); the estimate is D = mean over the 3 launches of d_b, with variance = sum over launches of (s_b(L)^2/n_b(L) + s_b(0)^2/n_b(0)) / 9, Satterthwaite degrees of freedom, exact t quantile. (b) **Scale of the tolerance.** For E2 the relative shift is D divided by the mean over launches of the level-0 means (offered pps, positive). For E1 and E3 the net metric is a difference of a measured cost and a constant, its level-0 mean is near zero or negative in some launches, so a relative 5% of it is meaningless; the shift D (identical for the net and the gross metric because the subtracted baseline is constant inside a launch) is therefore expressed relative to the mean over launches of the level-0 **gross** CPU per flow-scoped matched packet (busy CPU-seconds x 1e9 / matched, no idle subtraction). Classes MATERIAL / EQUIVALENT / INDETERMINATE and the family and overall premise rules are those of N2 with this shift. (c) **Per-launch idle baseline** (information only): the level-0 means of the net metric are also shown with each launch's own pre-flight idle rate (mean of its 3 windows) instead of 0.1307; it does not change D. (d) **Dose-response (post hoc, per family):** the metric regressed on the measured canary rate of the window with a separate intercept per launch (within-launch slope, with its 95% interval), next to the slope that adding the injected CPU alone would give (window x 1e9 / matched for E1; 0 for E2). (e) **N1 restated:** a Wilson upper bound of 0.10 cannot be reached with 30 windows even with zero flags (0/30 gives 0.114; at least 37 windows are needed), so the pre-declared acceptance test was unsatisfiable by construction; the pooled summary keeps it (and prints "NOT acceptable"), and A4 reports in addition the observed false-positive rate with its interval, the number of windows that the old criterion would need, and calls V8's false-positive rate acceptable if the observed rate is at most 0.10. No threshold of sections 5 and 6 (delta = 5%, class limits 0.9 and 0.1) changes.
